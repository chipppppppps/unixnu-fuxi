## 2. IPSW 里到底需要哪几个组件

用 `unixnu ipsw fetch` 走 HTTP range 只取需要的字节（**不下 6,835,124,840 B 的整包**）。

| 组件 | 成员 | 大小 | 用途 |
| --- | --- | --- | --- |
| `RestoreRamDisk` | `044-75545-038.dmg` | 184,549,403 | 恢复盘（IM4P 包着 176 MiB APFS） |
| `RestoreTrustCache` | `Firmware/044-75545-038.dmg.trustcache` | 5,921 | **不能用**（version 1，见 §3） |
| `StaticTrustCache` | `Firmware/044-76040-038.dmg.trustcache` | 59,519 | bundle 的 static 模块 |
| `Cryptex1,SystemTrustCache` | `Firmware/044-76034-038.dmg.trustcache` | 1,871 | bundle 的 system 模块 |
| `OS` | `044-76040-038.dmg` | 5,157,406,069 | 完整系统卷（本轮没用到） |
| `Cryptex1,SystemOS` | `044-76034-038.dmg` | 3,303,014,400 | 同上 |

### 恢复盘的真实格式

`044-75545-038.dmg` 名字像 UDIF，其实是 DER：

```
30 84 0b 00 00 15        SEQUENCE, 长 184,549,397
  16 04 "IM4P"           类型
  16 04 "rdsk"           子类型
  16 01 "0"              版本
  04 84 0b 00 00 00      OCTET STRING, 长 184,549,376
    <裸 APFS 容器>
```

`koly` 出现 0 次，尾部 512 字节全 0 —— `udif` 会把它当 raw 镜像（所以 size 会报 184,549,403，
差 27 字节外壳）。`NXSB` 在偏移 **32** 而不是 0，因为 APFS `nx_superblock` 先放 32 字节
`obj_phys_t`，`nx_magic` 在 0x20、`nx_block_size` 在 0x24、`nx_block_count` 在 0x28：

- block_size = **4096**，block_count = **45056** → 45056 × 4096 = **184,549,376** = 176 MiB 整。
- 卷 UUID `9071148B-B025-402D-AD7A-48464D8B5FFF` 在偏移 5,505,264 等 3 处（`APSB` 在 5,505,056），
  `launchd` 存在，`ramdisk` 出现 7 次 —— 与项目记录里 r2/r3 那块盘是同一份。

## 3. 信任链：为什么要自己拼 bundle

`DarwinBoot.c:371-400 ValidTrustCaches` 只接受这种容器：

```
u32 count
u32 offsets[count]
<module 0> <module 1> …
```

且每个模块起始必须是 `u32 == 2`（version 2），entry 数在 `Start+20`，
`End - Start == 24 + entries * 24`。

`RestoreTrustCache` 内层是 **version 1**（`16 04 "rtsc"` / `16 01 "1"` / 内层 `01 00 00 00`）
→ 检查失败 → `DarwinBoot.c:675` 返回 `EFI_COMPROMISED_DATA` → 回菜单 + 一行小字，
**绿条之前就死**。这就是 `boot_v2.img` 的全部现象。

自己拼的 bundle（`scripts/pack-trust-bundle.py`）：

```
count   = 2
offsets = [12, 59508]
static  = 59,496 B / 2478 entries  sha256 da88460e6e513438d5307e5c526f76497a74754476a24da29f239f0c90120fc2
system  =  1,848 B /   76 entries  sha256 d121ba89167e03aafd00fa687c30cd8ebc4ccafd10c1408adb2ba3de12403651
bundle  = 61,356 B  sha256 7416ca4f8377146626bb284e2133c76bee6cb4e3ee0af5d648b186235a7323a7
```

最后那个哈希与 `UniXNU/profiles/os/ipados-17.7.11-21H461/profile.toml` 里
`[ipsw.sha256] trust_cache_sha256` 的第一项**完全相同** —— 拼对了就会对上，这是最省事的自检。

### v1 那份长什么样

```
version = 1
uuid    = cfc8a0d56fb24d6c8b9bd3976ce18057
count   = 267
entries = 267 × (cdhash 20 B + flags 2 B)，flags 全是 2，cdhash 严格升序
body    = 24 + 267 × 22 = 5,898 B
```

v2 的头部与它一致（`version + uuid + count` = 24 B），只是每条 24 字节（cdhash 20 + flags 4）。
所以 v1 → v2 **不是改一个字节，是逐条重新序列化**：

```
module = u32(2) + uuid + u32(267) + [cdhash(20) + u32(flags)] × 267   = 6,432 B
bundle = u32(1) + u32(8) + module                                    = 6,440 B
sha256 = 750b5d8ac5f5b52b8fd02d261caf96dd318db0904b3651ca05d9ae4939de488a
```

产物在 `work/trustcache/restore-v2.trustcache`，已按 `ValidTrustCaches` 的全部规则
（count ≤ 128、offset 4 字节对齐、模块 version == 2、`End - Start == 24 + entries*24`、
flags ∈ 1..4、cdhash 严格升序）逐条验算通过。

### 与 2026-11-03 记录的对照（重要）

`evidence/2026-11-02-first-boot.md:496` 记的 r3-ramblock：追加参数
`fuxi-touch=4 fuxi-touch-panic=2 rd=md0-ramblock` + packed 恢复盘 + **它的 trust cache** +
`root_match_volume_uuid`，镜像 SHA-256 `cd5a110268c79ce7`，结果是「面板出现带 SYS 行的报告」；
`:541-543` 进一步写明「pid 1 是 launchd，pid 3 restored_external，pid 4 mount_tmpfs，
两分钟内三个进程，**AMFI 让它们跑起来了**」。

也就是说：**那次用户态真的活了，我们这次 PID 1 死了**，我们并没有比公开记录走得更远。
差别只能出在 trust cache —— 这条路上 `kernel.macho.trustcache` 是唯一的签名输入，
而 `ValidTrustCaches` 硬性要求 version 2。既然 r3 能跑起来，它们当时喂进去的必然是一份
**version 2、覆盖恢复盘那 267 个 cdhash** 的文件（即上面这份转换产物），
而不是 `ipsw fetch RestoreTrustCache` 直接吐出来的原始字节。

我们这次喂的是两模块 bundle（static + system）：它覆盖 OS / SystemOS 卷里的二进制，
**不包含**恢复盘 `/sbin/launchd` 的 cdhash。这正好解释了现象：launchd 能 exec 成功
（所以没有 `Process 1 exec of … failed`），随后被 AMFI 杀掉，`initproc_spawned` 仍是 FALSE，
内核打出 `initproc failed to start`。

→ 下一步（**已做并验证**）：`--trust-cache` 换成那份 6,440 B 的转换产物，其余不动。
`scripts/pack-restore-trust.py` 就是这一步的实现，run 42356995919 用它构建，
真机上 `SYS` 行出现 `1:launchd 3:restored_esterna 4:mount_tmpfs n3` —— 推断成立。

## 4. 恢复盘怎么进内核（fuxi 的特殊之处）

| 尝试 | 结果 |
| --- | --- |
| `bootimg --ramdisk <恢复盘>` | **不行**。`carrier == 'image'` 时 `--ramdisk` 参数就是 payload 卷本身（`bootimg.py:114-127`），之后还会被换成 `uefi/Resources/ramdisk` 占位 |
| `--data-ramdisk` + `[payload.adt] packed_data_ramdisk = true` | **正解**。payload 卷里出现 `Payloads/scratch-data.img`，`unixnu.toml` 多一行 `initrd = "Payloads/scratch-data.img"`，ADT 里出现 `PackedRAMDisk` 节点 |

打盘（`scripts/pack-data-ramdisk.py`，只留非零页，格式见 `PackedRamdisk.h`）：

```
raw     184,549,376 B  (176 MiB)   sha256 aadb59ed21a8f0218a348f070913ab5a7679805c58408534d811170871f1fc05
packed  137,445,888 B  (131.1 MiB) sha256 fab7639b00c9683403c0e4a0a3641b04d04d4fcffadb38319d3e237c7d96c841
extent  30 个, ratio 0.7448, 覆盖到逻辑偏移 158,924,800（尾部 25 MiB 全零，省略）
```

项目记录里 r3 那块是「0x8193 pages = 129.5 MiB」= 33,171 页，我们是 33,556 页，差 385 页
—— 量级一致，不是同一份字节，但足以走通同一条路。

根卷怎么被找到：`NativeRamBlock` 把内存盘发布成 `IOMedia` → APFS attach →
`IOFindBSDRoot` 按 `root_match_volume_uuid` 匹配 → `vfs_mountroot`。
`bsd_init` 在非 macOS 启动时要求根卷密封签名（`FSIOC_KERNEL_ROOTAUTH`），只有
`bsd_rooted_ramdisk()`（判断 `rd` 参数前缀是不是 `md0`）为真才跳过 —— 所以
`rd=md0-ramblock` 必须加，且长度不能是 3 字符（否则会当成设备名而不是跳过标记）。

## 6. 真机结果与解读

### 第一次（`boot.img`，11.7 MB）

绿 → 蓝 → 品红三色带全出，随后 panic：

```
Failed to mount root device @IOKitBSDInit.cpp:984
pages=0x0000000000127053  free=0x0000000000125a38
```

这一版 payload 里没有恢复盘，根卷无从谈起。但同样参数下项目自己也记录过同一行
（`evidence/2026-11-02-first-boot.md` 的 `h1-hid`），说明我们复现了它们的基线。

重刷一次并**持续点屏幕**后，触控探针抢在等根设备超时之前 panic，打出了 §1 里那两行 FTS 和
`SMP … run7`（7 个副核全部起来）。

### 第二次（`boot_v2.img`，144.7 MB）

停在 UniXNU 菜单，一个选项列表 + 一行小字，**没有任何色带**。见 §3：trust cache 是 version 1。
源码上完全对得上 —— 菜单小字来自 `Main.c:160-167` 的 `'%s' returned: %r`，绿条在
`DarwinBoot.c:811` 才画。

### 第三次（`boot_v3.img`，144.7 MB）

**绿条（上）+ 蓝条（下）** → 屏上出文字 → 停住，首行：

```
initproc failed to start
```

`bsd/kern/kern_exit.c:1806-1832`（`proc_handle_critical_exit`）：

```c
if (p == initproc) {
        if (strnstr(p->p_name, "preinit", …)) prefix_str = "LTE preinit process exited";
        else if (initproc_spawned)            prefix_str = "initproc exited";
        else                                  prefix_str = "initproc failed to start";
}
panic_with_options(0, NULL, DEBUGGER_OPTION_INITPROC_PANIC,
    "%s %s -- exit reason namespace %d subcode 0x%llx description: %s", …);
```

`initproc_spawned == FALSE` → PID 1 还没生出子进程就退了。而 `load_init_program`
（`bsd/kern/kern_exec.c:6891-6948`）只在 exec 直接失败时 panic `Process 1 exec of … failed`，
没有出现 → **`/sbin/launchd` 是 exec 成功的**。

对照 `UniXNU/scripts/check-original-launchd-integrity-checkpoints.py:29-33`：AMFI 杀进程时前缀会是
`CS_KILLED initproc failed to start`（namespace 3 / code 2 / description none）。我们首词不是
`CS_KILLED`，倾向不是签名杀。

里程碑因此推到：UEFI ✅ 菜单 ✅ payload ✅ DarwinBoot ✅ 内核入口/MMU/7 副核 ✅
**根卷（APFS 内存盘）✅** 用户态 ❌。

> 但这不等于「比公开记录更进一步」：2026-11-03 的 r3-ramblock 已经让 launchd /
> restored_external / mount_tmpfs 三个进程活过。我们这次反而退了一步，
> 原因见 §3 末尾的对照 —— trust cache 喂错了。**第四次已修正，见下。**

### 第四次（`boot_v4.img`，144,691,200 B，sha256 `9cdfb91f…`）

`payload` 里只有一处不同：`kernel.macho.trustcache` 从 61,356 B 的 static+system bundle
换成 6,440 B 的**恢复盘 v2 转换产物**（`scripts/pack-restore-trust.py`）。
其余（kernel、adt、137 MB 恢复盘、`rd=md0-ramblock`）逐项相同。

上机：`Sending 'boot.img' (141300 KB) OKAY [2.977s]` + `Booting OKAY [0.054s]`，
→ 绿条、蓝条，**然后屏幕上没有文字**。

「没有文字」这次是好消息：`panic_screen = true` 时任何 panic 都会打印，不打印 = 没 panic。
为了确认内核与用户态都活着，点一下屏幕让触控探针在抬手时 panic，报告出来了：

```
FTS … （两行探针数据）
SYS root apfs /dev/disk1s1 1:launchd 3:restored_esterna 4:mount_tmpfs n3 @FuxiTouchProbe.cpp:590
```

- `/dev/disk1s1`：根卷是 APFS，来自 NativeRamBlock 的内存盘；
- `1:launchd`：PID 1 活着（AMFI 接受了它 —— 这正是 §3 推断的验证）；
- `3:restored_esterna`：真机屏幕上名字被截断成 15 字符，即 `restored_external`，恢复模式的界面进程；
- `4:mount_tmpfs`：恢复盘的第三个进程；
- `n3`：三个进程。

与 2026-11-03 的 r3-ramblock 记录（`1:launchd 3:restored_externa 4:mount_tmpfs n3`）逐字一致。

**结论：第 7 环打通。** 内核在跑、根卷是 APFS、PID 1 是 launchd、restored_external 起来了，
没有 panic。看不到界面只是因为这条线没有 Display/GPU 驱动，恢复盘的用户态在跑但没人给它画面。

## 7. 三条墙

1. ~~信任链格式~~ **已解决**：恢复盘的二进制由 version 1 的 `RestoreTrustCache` 担保
   （267 条 cdhash），而内核与 DarwinBoot 只认 version 2 容器。解法是按 v2 逐条重序列化
   （§3，6,440 B），把**恢复盘自己的** cdhash 交给 AMFI —— 换成 static+system bundle
   就会停在 `initproc failed to start`。
2. **没有真存储**：内核里 UFS 驱动为 0（`AppleUFS` / `IOUFS` / `UFSDevice` 字符串计数全 0），
   根卷是 137 MB 打进 payload 的内存盘。恢复盘的设计目的是「一次性装机」，不是长期系统。
3. **没有显示**：Display / GPU 在 fuxi 线上仍是 `planned`，panic 屏靠 UEFI framebuffer 的文本。
   用户态在跑，但没有东西能画到屏上。

顺带回答「会不会变砖」：镜像里没有任何存储驱动，`fastboot boot` 也不写分区，
内核无法触及 userdata，物理上写不了任何东西。

- 内核参数走真 UFS 根（`native-fuxi-ufs-root=1`、`offline-apfs-load=1`、
  `offline-mobile-graphics-load=1`、`boot-ui-focus4=SpringBoard` 等），不做内存盘；
- 另有 `shim/fuxi-loader`（第二核跑 USB 监控）+ 自写 USB 调试通道，可以从 PC 发手势和截图。

它们 README 明确说不发布镜像/IPSW/密钥，所以没有可直接刷的包。补丁与我们的内核版本不兼容，
搬不过来。

## 9. 这一天的代价（踩坑清单）

| 坑 | 代价 | 结论 |
| --- | --- | --- |
| `gh run download` 卡死 | 11 分钟 | 大产物一律走 `tools\chunked_download.py` |
| `Invoke-WebRequest` 92–95 秒断流 | 5 次失败 | 代理不让长连接，必须分块 |
| 分块下载第一块 403 | 1 轮 | API 302 到签名 blob 时不能带 `Authorization` |
| `decrypt.cmd` 相对路径 | 1 轮 | `%~2` 改 `%~f2` |
| `workflow` scope（404 伪装） | 约 40 分钟 | 自己走 device flow；`gh auth refresh` 在非 TTY 挂死 |
| trust cache version 1 | 一次构建 + 一次上机 | 见 §3，这是整条链最容易误判的地方 |
| **信任的对像错了**（static+system bundle 对恢复盘） | 一次构建 + 一次上机 | 哈希与 profile 钉的一致 ≠ 覆盖了恢复盘的 `/sbin/launchd`。§3 末尾 |
| `rebuild.ps1` 里 `$image` 与参数 `$Image` 同名 | 1 轮 | PowerShell 变量不区分大小写，循环变量改名 `$imageJob` |
| PowerShell 5.1 不支持 `??` / `if` 表达式 / 按 ANSI 读 .ps1 | 若干次 | 脚本保持 ASCII、用语句 |
